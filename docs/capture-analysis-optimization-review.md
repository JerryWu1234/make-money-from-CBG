## 1. P1：失败后可能先启动下一角色，再由 E2E 轮询暂停

**确定事实与现象**

- `server/analysis/runner.ts:313-332`：装备结果不能继续时调用 `deferPricing()`，然后 `continue`；宝宝和宝宝装备分别在 `379-390`、`443-457` 走相同路径。
- `server/analysis/store.ts:670-680`：`deferPricing()` 只把当前任务设为 `waiting_pricing`，不暂停批次。`637-642` 的 `next()` 会选择下一条 queued 任务。
- `tests/live/streaming-valuation.live.ts:86`、`389-429`：E2E 每轮暂停 2 秒，读到失败状态后才调用 `stopForRepair()`；`117-134` 才向采集和分析服务发出暂停请求。
- `resume-unnamed-accessory-2026-10-15-live.log:77-79`：先出现第 8 角色在查装备，随后出现 `completed=7, waitingPricing=1` 且 current 已换成下一角色，再出现 repair 提示。这证明暂停前已有下一角色启动。

**影响**

“失败先停”目前依赖外部测试的轮询。轮询间隔、状态请求和暂停请求期间，下一角色可能已经打开页面或产生请求。正常产品流程若没有同样监控，也不会由这段 runner 自动停下。AI 非致命错误还有一次自动重试路径（`runner.ts:519-534`），与“首次失败即停”的约定也需要统一。

**最小建议**

在服务端首次确认真实查价/分析失败时，保存当前任务并暂停批次，然后返回，保留已有 completed 和 queued 数据。由现有协作层同时请求停止采集。E2E 继续监控和验收，但不承担唯一的暂停职责。不要把正常预算分段、已有进度推进或明确无样本当失败。

**业务影响与确认**

会改变失败后的调度行为：下一角色不再继续，AI 也不应先自动重试。此项直接落实已经明确的“失败先停”；父流程在第 9 个角色出现新错误后的安全暂停点完成修复。本报告没有实施。

**后续验收**

先列出“查价读取失败、AI 校验失败、正常分段推进”三类情况，再测。失败场景的 E2E 产物应保存任务状态与调用顺序，证明失败点后没有下一角色的新请求，且续跑仍使用原批次。

## 2. P2：宝宝与宝宝装备缺少人物装备那样的逐件保存点

**确定事实与证据**

- 人物装备已支持逐件保存：`server/analysis/equipment-pricing.ts:662-671` 逐项调用 source，处理后调用 `onCheckpoint`；`runner.ts:299-306` 立即入库。
- 宝宝接口 `runner.ts:27-37` 没有 checkpoint 参数；`pet-pricing.ts:725-737` 把全部待查宝宝交给一次 `findCandidates()`；`browser-pet-source.ts:1608-1637` 在 source 内按宝宝顺序处理，`2393` 才返回全部结果。runner 在 `370-379` 收到整份结果后保存。
- 宝宝装备也在 `pet-gear-search.ts:93-99` 等待全部候选返回，runner 在 `437-443` 才保存。
- 当前 source 有 240 秒软截止（`browser-pet-source.ts:1551`），runner 还有 300 秒取消边界（`runner.ts:358-363`）。这使“正常返回已查部分”与“异常/取消后没有返回”有不同的保存结果。

**影响与不确定性**

若后面的宝宝发生异常、进程退出或用户暂停，本轮前面宝宝在 source 内已经做完的工作可能尚未入库；续跑要重做。已有上一轮快照仍会保留，不代表全部历史丢失。**这是源码可确认的保存窗口；本次没有注入故障，也没有证明真实批次因此丢失过某一只宝宝结果。**

**最小建议**

沿用现有人物装备的 checkpoint 形式，在每只宝宝/每件宝宝装备完成并通过校验后保存。只增加保存边界，不更换 source、比价策略或队列模型。

**业务影响与确认**

报价规则不变，但会改变中间进度的保存时机，增加数据库写入。属于可选改进，可后续单独安排。实现前先覆盖“首只完成后第二只失败、暂停、正常软截止”三类失败方式；E2E 保存中断前后快照，证明已完成项不被重做。

## 3. P2：45 分钟/16 轮是一次连续执行的预算，续跑会重置

**确定事实与证据**

- `runner.ts:222-244` 在 `process()` 内创建内存预算；换 task 时也重新创建。
- `runner.ts:186-188` 每次 resume 都重新 launch/process。因此同一角色暂停再继续会重新获得预算。
- `store.ts:682-690` 保存了 round/startedAt 作为进度；`store.ts:890-895` 重试还会清空这份进度，但 runner 本身也不从持久化进度恢复预算。
- `runner.ts:259-264` 只在 while 顶部检查总轮数；装备、宝宝、宝宝装备分别在 `288`、`366`、`433` 加一。若一个循环连续完成多个阶段，16 并不是每次调用前的严格上限。

**影响与不确定性**

当前实现能限制一次连续执行，但不能限制同角色多次续跑的累计耗时/轮数。人工修复等待也不计入下一次预算。这可能正是希望的“修复后给新机会”，不能直接判定为 bug；目前“本角色自动查价上限”的文字没有说明这个边界。本次未做耗尽预算的动态试验。

**最小建议**

先明确预算是“每次人工续跑”还是“同角色累计”。若维持现状，只需把范围写清；若需要累计，持久化已消耗的自动查价时间与轮数，人工等待单独排除。若 16 为严格硬上限，应在每次 source 调用前检查，而非只在循环顶部。

**业务影响与确认**

这是范围选择，必须单独确认。累计预算会让反复续跑更早停下，可能影响现有长流程，不应顺手更改。

**后续验证与修复**

新增边界用例已复现：装备在第16轮完成时，旧实现会直接开始第17轮宝宝查询。现在装备和宝宝阶段完成后回到原有预算检查，再进入下一阶段。测试确认第16轮后暂停、已完成装备保留，显式重试从宝宝阶段继续。45分钟/16轮仍按一次连续执行计算；累计预算口径未改变。

## 5. P3：相同查价证据有多份内嵌，状态接口仍需读解析大结果

**确定事实与证据**

- `pricing-progress.ts:175-183` 每轮同时保存 rawResponse、searchItems，并把 searchItems 累加到顶层。rawResponse 本身也是整份响应的 JSON（例如 `pet-pricing.ts:734-737`），含相同记录。
- `store.ts:728-736`、`792-799` 每次更新整份 pricing JSON。`next():640-667` 每轮重新取出并解析它。
- 状态 API 已使用 summary（`server/api.ts:134-143`），但 `overview():1014-1032` 仍先选择 result_json；结果列表在 `1073-1101` 也先完整 JSON.parse，再在应用内去掉大字段。summary 减少了传输量，没有消除数据库读取和解析这些字段的成本。
- 15:35 只读快照：第 2 角色 pet_pricing_json 为 **13,079,483 UTF-8 字节**；其中历次 rawResponse 共 4,172,236 字节，顶层 searchItems 按 Python 默认 JSON 编码约 6,473,992 字节。它们包含交叠证据，不能把这些数字直接相加当作可节省量。
- 历史产物 `status-summary-verification.json` 记录 summary 从约 11.95 MB 降到约 94.97 KB、查询约 143 ms；这是已有传输优化的历史结果，不是本次性能测量。

**影响与不确定性**

数据量和重复内嵌可以直接确认。同步 SQLite 读取及 JSON 解析会占用 Node 执行时间；持续状态轮询也会重复这些工作。**本次没有压测，不能把这些开销说成真实超时或页面失败的确定原因。**

**最小建议**

先测当前状态接口的读取/解析时间。若确有瓶颈，先让状态接口从数据库只取展示必需的字段，详情页继续保留完整证据。历史证据去重应另立工作项，保持可核验 hash 与原始内容，不在性能优化时删除历史记录。

**业务影响与确认**

仅优化状态查询可保持报价行为不变；调整历史存储涉及迁移和复核成本，需要单独确认。它不是当前报价故障的必需修复，也不建议现在增加一套通用存储框架。

**后续测量与最小优化**

实际10角色库的状态接口三次读取为985、977、928毫秒。只读对照将重证据字段先在SQL摘要中移除，再沿用原摘要渲染，输出逐字段深相等；首次对照三次约545、545、556毫秒，后续测量有632–1090毫秒波动。已将此小改应用到摘要SELECT，详情及保存的原始证据不变。该结果说明减少了大JSON传输和解析，不能据此认定浏览器超时的唯一根因，也未做历史存储去重。
