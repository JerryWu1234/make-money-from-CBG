## 5. 正常分析流程

1. 核对仓库、分支、服务cwd及真实数据库，保存本次代码版本、规则版本和开始时间。
2. 在访问被允许且登录有效的前提下，重新采集验收角色，确认当前在售状态、售价及完整资产清单；保留历史快照。
3. 从新的数据库快照生成逐件任务。类型判断依靠资产元数据及属性，不依靠某个角色ID或固定装备名称。
4. 正常“分析”流程自动调用各类搜索。无需另一个“补齐估值资料”按钮，也不要求用户复制价格或逐件手动搜索。
5. 每类使用自己的搜索／详情页面，保留原采集页、筛选、页码和断点。采集与分析可共存；只对实际冲突的页面操作协调，不能一概要求暂停采集才能查价。
6. 精确搜索无有效样本时，依次执行可解释的相近搜索，保存每次条件及放宽原因。候选仍需独立详情核验。
7. 收集报价及计算均价，及时保存逐件结果，前端已完成项目立即显示。
8. 执行宝宝装备查价及包价核对，计算裸号、人物资产、宝宝和整号参考金额。
9. AI读取已经保存的资产报价快照，负责解释和风险说明；价格及合计由程序复算，AI不能自行编数字或用搜索摘要补金额。
10. 刷新页面、重新点击分析或服务恢复时继续未完成资产；有效已完成资产及兼容的AI结果不能重复分析。

单角色验收必须只选定该商品，不意外启动全部221条历史商品。现有 `startAnalysis`、任务选择与普通分析调用链应优先复用；无需新增一条只对本样本有效的脚本路径。

## 6. 精确与相近匹配

精确组优先。同一件资产的精确与相近组不能悄悄混算；若最终采用相近组，记录具体配置差异。

- 人物装备与灵饰默认保持类型、等级、特技特效及交易限制。数值相近使用公开、固定的容差，筛选下限与详情比较必须一致；不同宝石／精炼等级或套装等级的样本需要明确分组及差异，不编造折价系数。
- 当前人物装备数值比较以相对20%及部分小数值绝对容差为基础，具体字段见 `equipment-match.ts`；不要在表单里放宽、详情里仍要求全部原文相同。
- 宝宝以实际类型、保护技能和核心用途匹配。当前通用比较包含等级±5、基础资质±15%、成长差≤0.03；普通技能共有至少2项且覆盖双方至少60%。须弥、未知／特殊技能，以及须弥法宠的高级法术连击／高级魔之心等核心配置保持保护。使用这些限制时在报告中展示实际差异。
- 数值0、缺失、未知是不同状态；资质基础值和额外加成也是不同字段。避免把换行加成重复算入资质，或把昵称误当宝宝名称。
- 元身及玉魄目前代码主要采用精确描述匹配。若仍找不到样本，应评估并实现字段级相近匹配；不能直接把普通装备比较器套过去。类型、属性槽位、特殊效果及有效期等必须保留语义。
- 正常可修装备耐久差异不能单独抹掉可用报价；零耐久、无法修理、修理失败及交易限制单独核验。

每个拒绝候选都应有具体原因，如类型不同、保护技能不同、主属性不符、详情缺失、价格单位冲突或已下架。不能统一写成“搜不到”。

## 7. 前十件均价与分页

按官方结果的原始页序、行序处理，先核验、去重，再取前十件有效商品。不能改取最低的十件，也不能按属性距离重排后另选十件。

有效报价至少满足：同类和选定匹配组、独立主商品身份正确、完整可见详情、当前在售、明确人民币挂牌价、读取时间有效、价格与保存证据一致。推荐商品、诊断价、重复商品及未通过匹配的列表价不计入。

同一个商品的不同URL别名按同一身份去重；同一商品出现冲突报价应重新核验，不可任取一条。币种／单位不能猜测，人民币分与元转换只做一次。

计算使用人民币分，最后四舍五入到分：

`平均挂牌价 = 已采用报价之和 ÷ 实际样本数 N`，其中 `1 ≤ N ≤ 10`。

找到十件后，保存这十件及采用顺序；第十一件不参与均价。结果不足十件时，只有确认选定匹配组的结果已真正读完，才可按实际N件计算，并显示样本数、价格范围及限制。精确组已穷尽但有少量有效报价时，可采用该组实际数量，无需为凑十件混入另一组。

单次三页预算、60行预算、详情预算、超时、登录失效或验证码，都不是结果穷尽。必须保存页码、结果终点或下一页状态、排除计数及读取失败数量来证明是否读完。价差超过1.5倍可以提示风险，但不能直接丢掉已核实均价。

## 8. 进度和证据保存

复用现有 `EquipmentPricingSnapshot`、`PetPricingSnapshot`、`PetGearPricingSnapshot` 和游标，不优先新增平行的数据模型。

每件资产至少保存：

- 资产唯一键、角色商品键、原始属性与输入hash、查询策略／计价版本；
- 搜索页面、筛选阶段、数据库字段到控件的映射、填写动作及实际提交条件；
- 商品唯一身份、URL、标题、人民币价格、主详情证据、读取时间、sourceHash；
- 精确／相近类别、属性差异、采用或拒绝原因、页码／行位置及采用顺序；
- 目标数量10、实际有效数量、均价、最小／最大挂牌价；
- `searchState`、是否真正穷尽、后续游标、失败详情及重试原因。

`pending`／`read_failed` 不能生成完整资产参考金额。`completed` 只说明搜索流程结束，仍须单独判断是否有可用报价。报价有效期沿用当前24小时规则；规则、字段、库存或筛选计划改变时，旧样本和旧游标不能直接混用。

刷新后从保存的阶段、页码和行位置继续，并核对该页结果身份及顺序是否变化。结果变化时不能直接沿用旧行号跳过新商品；须重新核验已采用顺序，必要时重建取样组。已保存商品必要时重验最新在售状态，但不能把同一报价重复计价。反复点击不能产生重复执行器、重复AI任务或多个同时占用同一任务的owner。

原始搜索尝试保存于数据库用于审计；发给AI的内容仅保留必要的报价摘要和依据，不把完整原始搜索请求／响应混入Prompt。

## 9. 无报价、特殊资产及整号核算

必须区分：采集不完整、字段无法识别、表单未生效、搜索未穷尽、详情读取失败、真实无匹配、不可交易以及权限拒绝。采集、解析、填表、未穷尽、详情读取及权限问题不能推断装备廉价；真实无匹配另按下述规则处理。

用户允许对真正搜不到的低值资产不再反复纠缠。实施时只能在合理精确／相近阶段已穷尽且无读取失败的情况下，将项目标为“无匹配，未计入参考合计”，保存筛选与穷尽证据。`referencePrice` 仍为空；不能把“未计入”伪装成市场价0元。合计须披露排除项目，不称全部资产均有实价。

专用／绑定资产不能因为无法独立交易就推断低值。例如本样本的碧玉剑专用玩家46377146，不能直接套普通可交易剑价。需要单列其角色用途及整号价值影响；若无法取得可解释依据，保留未知，不能假造单件报价。

采用宝宝包价前，逐个核验样本随身装备的数量、类型、等级、关键属性、镶嵌和套装是否与目标兼容；缺失装备信息不能假定为裸宝宝或完整包价。宝宝挂牌若已经包含随身装备，整号计算只加宝宝包价一次，宝宝装备均价作为独立交叉核对。若未来采用裸宝宝价加装备的方式，必须证明宝宝样本不含装备并明确拆分依据，不能默默切换两种核算方式。

完整资产加总应满足裸号及需计价的人物资产、宝宝都有可靠金额。存在无法定价资产时展示已知小计、缺项及排除项；不能把历史挂牌减裸号所得差额当成装备／宝宝价值。若使用整号市场样本覆盖专用等特殊资产，单列该方法，不冒充逐件价格加总。
